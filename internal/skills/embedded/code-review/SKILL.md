# 代码审查

核心纪律：**审的是改动，不是全仓库**。没先拿到 diff 就开始逐行点评 = 没读代码。

## 流程

### 1. 拿范围

- 有 git：`git diff`（未提交）或用户指定的 commit / PR 范围；
- 无 git 或改的是散文件：让用户圈定文件，或按本次实际改动的清单。
- 读完 diff 后，再读每个改动点的上下文：调用方、被调接口、相关测试。
  离开上下文判断「这段对不对」基本是猜。

### 2. 按严重度过五关

每个改动点依次问：

1. **正确性**（必须查）：边界（空 / 0 / 1 / 超大 / 并发）、错误路径（错误被吞？重试幂等？）、资源泄漏、状态一致性；
2. **安全**（必须查）：注入（SQL / 命令 / 路径穿越 / XSS）、硬编码密钥、越权（接口没校验归属）、反序列化不可信输入；
3. **性能**（有数据量才查）：N+1 查询、循环内 I/O 或序列化、O(n²)、缺索引、大对象常驻；
4. **可维护性**（抽查）：命名、重复逻辑、注释与实现不符、多余抽象 / 防御代码、与周边代码风格脱节；
5. **测试**：改动有没有测试覆盖？断的是行为还是实现细节？边界用例在不在？

### 3. 输出

- 按 `Blocker / 建议 / 吹毛求疵` 三档分组；
- 每条必须带 `file:line` + 为什么是问题 + 具体修法（能给示例代码就给）；
- 总数控制在 10 条内：宁缺毋滥，纯风格问题（空格、导入顺序）交给 linter，不提；
- 结尾一句话结论：可合并 / 修完 Blocker 可合并 / 有 Blocker 不能合并。

## 反模式

- 没读 diff 就下结论；
- 每个文件都挑风格毛病，把真问题淹没；
- 「这里可以优化一下」式空话——必须指到具体行、说明为什么、给改法；
- 审查范围外的旧代码开新账（顺带发现的 Blocker 级问题单独标注「非本次改动」）。
